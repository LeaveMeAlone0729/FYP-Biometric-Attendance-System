# Stage B3 — working device face/liveness tests, activation disabled

## Security boundary

B3 executes server-side face matching and liveness for a KEY_PROVEN candidate.
It does NOT implement institutional biometric trust or recovery. Every result is
UNTRUSTED_TEST_RESULT, with trusted=false, consumable=false,
activation_eligible=false and activation_enabled=false. There is no activation
route. The original UnavailableTrustedApprovalProvider and hard activation stop
remain in place; B3 sessions cannot be consumed as trusted approval grants.

Biometric matching proves a match to the existing enrolled template only. Its
provenance remains untrusted, including DEMO001. No template is enrolled, deleted,
replaced or upgraded to trusted by B3. Do not promote these test sessions into
future trusted grants; institutional revision/provenance and recovery checks must
be separately implemented and independently reviewed.

## Architecture and partner ownership

The new device-owned service imports unchanged partner functions: guided_face,
face, distance, hand, template decryption, image limits and frame constants. It
uses the existing FACE_DISTANCE_THRESHOLD and random gestures from one to five,
requiring three consecutive accepted face/hand frames. The algorithms, thresholds,
partner lifecycle service, existing biometric endpoints and attendance writer are
unchanged. No attendance or class session is created or called.

The partner Flutter CameraScreen combines capture and attendance API calls, so
B3 does not embed it. The independent device screen uses the same camera package,
front-camera initialization/disposal pattern and capture cleanup, with its own
face guide, server gesture instructions and progress. It uses ONLY
DeviceBiometricApi, never BiometricApi or the attendance camera screen. Existing
Android camera permission was already declared; native/Keystore files are unchanged.
Test helpers for the camera plugin and monotonic clock are reused read-only from
the partner's existing test helper file.

## Session, replay and logging rules

- Authenticated login and an owned, unexpired KEY_PROVEN pending request are mandatory.
- Bind student, exact login-session hash, pending ID, candidate ID/fingerprint,
  operation=enroll_second_device, Slot 2 and original ACTIVE Slot 1 registration.
- Pin a SHA-256 binding of the current encrypted template value; validate it before
  each frame and after inference. This detects replacement/re-encryption but is
  not a trusted institutional revision or attestation.
- Session TTL is min(existing challenge setting, 90 seconds, pending expiry,
  login expiry). Camera initialization time counts. The pending request stays
  under its existing five-minute lifetime; creating a test never extends it.
- At most one open FACE/LIVENESS session per pending request, enforced by a
  generated nullable unique open_pending_id and student-row serialization.
- Start retries return the same valid session without resetting expiry. A completed
  test remains an untrusted result; subsequent frame submissions fail.
- Five new sessions per student per five minutes. At most 60 submitted frames per
  test, counting invalid/adjustment attempts. Wrong gestures reset consecutive
  progress; a different face terminates the test.
- Decoded-frame hashes prevent same-session replay, including reuse of the face
  frame as a liveness response. Incorrect-stage and concurrent replay requests
  cannot advance twice. This is not a claim of global replay/video-spoof resistance.
- Raw frames are decoded in memory, not archived in application tables/files.
  Camera temporary files are deleted after reading. Framework multipart buffering
  may use OS temporary storage, released by the framework; deploy request-size
  controls appropriately for shared-network hosting.
- Separate device_biometric_events logs issuance and PASS/FAIL reason codes. PASS
  here is an UNTRUSTED biometric test outcome, never a trusted-device decision.

## Working REST contracts

All routes use existing student bearer authentication. POST create accepts strict
JSON; frame routes accept multipart form-data containing ONLY `file`. Client PASS,
trusted flags, student IDs and extra frame form fields are rejected/ignored by no
approval path: extra form keys specifically return INVALID_FRAME_INPUT (422).

### POST /api/v1/device-approvals

```json
{"pending_registration_id":"SERVER_PENDING_ID"}
```

HTTP 201 example (IDs/timestamps are generated by the server):

```json
{
  "success": true,
  "approval_id": "SERVER_TEST_SESSION_ID",
  "pending_registration_id": "SERVER_PENDING_ID",
  "candidate_device_id": "SERVER_CANDIDATE_ID",
  "public_key_fingerprint": "64_LOWERCASE_HEX_CHARACTERS",
  "operation": "enroll_second_device",
  "slot_number": 2,
  "stage": "FACE",
  "ready": false,
  "face_verified": false,
  "liveness_verified": false,
  "complete": false,
  "fingers": null,
  "valid_frames": 0,
  "required_frames": 3,
  "expires_at": "SERVER_ISO8601_TIMESTAMP",
  "expires_in": 89,
  "result_classification": "UNTRUSTED_TEST_RESULT",
  "trusted": false,
  "activation_eligible": false,
  "consumable": false,
  "activation_enabled": false,
  "message": "Center your face in the camera."
}
```

The legacy URL name approval_id identifies an untrusted biometric TEST session,
not a security capability or activation token. No trusted grant is issued.

### POST /api/v1/device-approvals/{id}/face

Authenticated multipart body: file=<fresh image>. Guided detection/position issues
return FACE with ready=false and adjustment instructions. A different face returns
FACE_NOT_MATCHED (403) and terminates the test. A match changes stage to LIVENESS,
sets face_verified=true and fingers to a fresh server-generated value 1..5.

### POST /api/v1/device-approvals/{id}/liveness/frame

Authenticated multipart body: file=<fresh face-and-hand image>. Match the enrolled
face on every frame and the server's hand gesture. A wrong/missing gesture resets
valid_frames to zero and returns instructions. Three consecutive valid frames
return stage=COMPLETED_UNTRUSTED, face_verified=true, liveness_verified=true,
complete=true and the message:

`Biometric checks completed — awaiting trusted biometric approval`

All trust/consumption/activation booleans remain false. No registration, attendance,
class session or existing verification-attempt row is inserted or changed.

### GET /api/v1/device-approvals/{id}

Return the current server-confirmed test state with the same bindings and flags.
Use it after an uncertain upload response rather than replaying the same frame.
It revalidates login, pending expiry and template binding. It does not refresh TTL.

Errors use the existing device envelope: success=false, code, message. Examples:
CANDIDATE_PROOF_REQUIRED (409), PENDING_EXPIRED/BIOMETRIC_EXPIRED (410),
BIOMETRIC_SESSION_NOT_FOUND (404 for wrong owner/login), FACE_NOT_MATCHED or
FACE_SUBSTITUTED (403), TEMPLATE_CHANGED (409), FRAME_REPLAY/BIOMETRIC_STAGE_INVALID
(409), BIOMETRIC_RATE_LIMITED/FRAME_LIMIT_REACHED (429),
BIOMETRIC_TEMPLATE_REQUIRED/BIOMETRIC_TEMPLATE_UNAVAILABLE (409),
BIOMETRIC_ENGINE_UNAVAILABLE (503). No client-provided biometric result is accepted.

## Flutter flow

1. Retain/reuse the candidate Android Keystore key and obtain a current KEY_PROVEN
   pending request under this login. An older request may need renewal after expiry.
2. Open facial recognition and liveness, then tap Start facial verification.
3. Only after the server creates/recovers a valid biometric test does the camera open.
4. Automatically upload fresh face frames, then show the server's liveness gesture
   and progress and upload new face/hand frames.
5. On completion, release the camera and show untrusted completion, explicitly
   stating Slot 2 remains inactive. No activation button exists.

The device adapter checks session revision and all inactive/untrusted flags. It
rejects a response claiming trusted/consumable/activation status or another bound
candidate. Network uncertainty reads status, rather than resending a consumed
frame. Permission denial offers camera retry; no-front-camera errors mention the
emulator webcam. Pause/navigation/completion dispose capture; late initialization
is disposed safely. The monotonic countdown never turns a result into authorization.
Existing automatic Phase 2 verification and all native keys/aliases are untouched.

## Safe emulator/tablet testing

Use the SECOND device only. Do not uninstall/clear/update the Samsung as part of
this test and do not delete/re-enroll DEMO001's face to force a match.

1. Start a tablet AVD with its front camera set to webcam0 (a real host webcam),
   or use a physical Android tablet. Cold boot the AVD after camera changes and
   close other applications using the webcam. Camera permission is required.
2. The backend must be running at its existing local address after B3 migration.
3. Explicitly choose the tablet/emulator serial. Build and install in place:

```powershell
Set-Location 'C:\FYP\FYP-Biometric-Attendance-System'
# Start only if the backend is not already running:
.\backend\venv\Scripts\python.exe -m uvicorn main:app --app-dir backend --host 127.0.0.1 --port 8000 --no-proxy-headers --reload
# In another PowerShell terminal:
$attendanceAdb = "$env:LOCALAPPDATA\Android\Sdk\platform-tools\adb.exe"
& $attendanceAdb devices -l
$attendanceCandidate = 'emulator-5554' # replace with actual candidate serial, never Samsung
& $attendanceAdb -s $attendanceCandidate reverse tcp:8000 tcp:8000
Set-Location 'C:\FYP\FYP-Biometric-Attendance-System\frontend'
& C:\Users\yap10\flutter\bin\flutter.bat build apk --debug --dart-define=API_BASE_URL=http://127.0.0.1:8000
& $attendanceAdb -s $attendanceCandidate install -r build\app\outputs\flutter-apk\app-debug.apk
& $attendanceAdb -s $attendanceCandidate shell am start -n com.example.frontend/.MainActivity
```

If installation fails, stop; do not uninstall as a workaround. Sign in as the
student whose existing enrolled face is being tested. Prepare SH tablet with its
retained key; a new login cannot reuse an older session's pending request. Open
facial recognition and liveness and start. Center the face until matched, then
show the random number of fingers on one hand, palm toward the camera, keeping
the face visible. Expect untrusted completion and inactive Slot 2. Do not submit
synthetic frames or test flags outside automated isolated fixtures.

A virtual scene may not contain a usable real face or hand. Use the host webcam
or physical second device if matching/hand detection cannot run on the AVD. Emulator
key proof and biometric tests do not establish physical device integrity. No emulator
or development authorization bypass is present. Real accuracy, lighting, and
spoof-resistance require consented camera evaluation; fixture tests verify workflow.
