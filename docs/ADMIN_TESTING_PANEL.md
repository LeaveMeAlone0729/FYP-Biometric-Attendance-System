# Local FYP admin testing panel

Branch SH. This is a small localhost-only operator UI over the existing Python
session/policy services. It is not a production administration system. It installs
no student-facing admin routes, modifies no biometric algorithms, and does not
change attendance/device approval rules or add BLE attendance enforcement.

## Start on the existing test laptop

Run from PowerShell 7 in the repository root. For a new teammate profile use
[the MySQL launcher](MYSQL_TESTING.md). For the existing original MariaDB profile
use [the original launcher](ORIGINAL_FYP_SETUP.md).

For an existing disposable MariaDB profile:

```powershell
# Existing guarded environment only: backend 8002, MariaDB 3322.
.\fyp-test.ps1 start
.\fyp-test.ps1 status

# ONCE: choose an admin username and a unique password (12–128 characters).
# Password entry is hidden. There is no default admin password.
.\start-admin-testing.ps1 -InitAdmin

# Optional read-only readiness/schema inventory check, then start the panel:
.\start-admin-testing.ps1 -CheckOnly
.\start-admin-testing.ps1
```

Open **http://127.0.0.1:8003/login** on the laptop. The panel binds only to
127.0.0.1; it is not for the tablet browser, LAN clients, proxying or tunnels.
Student credentials, including FYPTEST001, cannot log in as an administrator.
Use the existing test tablet app against port 8002 for the student workflow.

Stop the panel with **Ctrl+C** in its terminal. Stopping it does not stop or alter
the student backend/database. To stop those separately when finished:

```powershell
.\fyp-test.ps1 stop
```

The first command retains the environment's existing LAN/loopback setting; it
does not add firewall rules. To deliberately select a different listener, follow
the existing FYP_NETWORK_TEST_WORKFLOW.md. Never use the panel as attendance
network proof: its loopback connection is unrelated to a student's source IP.

### Startup diagnostics and first-time initialization

`fyp-test.ps1 status` READY proves the student backend is available; it does not
create a panel admin. A failed `-InitAdmin` leaves no usable `panel-admin.json`,
so normal panel startup must still refuse access. Initialization itself does not
need the backend/database to be running and never uses a database connection.

The launcher now reports a safe **stage**, **code** and exception type, without
printing exception values or credentials. For example:

```text
ADMIN_PANEL_NOT_STARTED: stage=credentials; code=ADMIN_CREDENTIALS_MISSING; error_type=FileNotFoundError.
```

`-CheckOnly` can run before initialization. If the environment passes but no admin
exists, it returns `result=SETUP_REQUIRED`, `backend_and_database=PASS`,
`admin_credentials=MISSING` and exit code 1. This is not a backend isolation
failure and does not allow starting an unauthenticated panel. After initialization
it returns PASS (exit code 0).

Run `-InitAdmin` directly in an interactive terminal, without a pipeline. Username
must be 3-40 letters/digits/`.`/`_`/`-`; password must be 12-128 characters and match
the confirmation exactly. Up to three corrections are allowed for length/mismatch.
Password input is never echoed; terminals without hidden input are rejected.
Hashing finishes before file creation. The file is published atomically without
overwriting an existing or concurrently created credential file. No credentials
are regenerated by `-CheckOnly` or normal startup.

Safe codes include PASSWORD_LENGTH_REQUIRED, PASSWORD_CONFIRMATION_MISMATCH,
PASSWORD_SETUP_ATTEMPTS_EXHAUSTED, INTERACTIVE_INPUT_REQUIRED,
INTERACTIVE_SECRET_INPUT_REQUIRED, ADMIN_ALREADY_EXISTS, PRIVATE_FILE_ACCESS_DENIED,
BACKEND_PROCESS_PROFILE_MISMATCH and BACKEND_NOT_READY_OR_NOT_ISOLATED. Correct the
named condition; do not disable guards, elevate the launcher or copy production
credentials as a workaround. Share only stage/code when reporting a failure.

### Browser login: Origin rejected fix

The original `Referrer-Policy: no-referrer` response header caused real Chrome
HTML form submissions to send `Origin: null`, even from the same local login
page. The exact-origin POST guard then correctly rejected that ambiguous origin
before credential/CSRF processing. GET /login did not require an Origin. The form
action was already the correct relative `/login`, and port 8002 was never used
as the panel's expected origin.

The minimal correction is `Referrer-Policy: same-origin`: local HTML forms retain
their actual origin while referrer information remains suppressed cross-origin.
The strict POST origin comparison, Host/loopback guards, session rotation and
CSRF checks are unchanged. `Origin: null`, missing Origin and cross-origin POSTs
remain rejected; a Referer header cannot override them. `localhost` and
`127.0.0.1` both work when used consistently, but they are distinct origins and
must not be mixed between a form page and its submission.

Restart only the panel to load the header change, then **reload /login** so the
browser replaces the old no-referrer document. Prefer
`http://127.0.0.1:8003/login`; `http://localhost:8003/login` is also supported.
Successful login redirects to the real Attendance Sessions dashboard at
`/sessions`. Existing backend/database processes need no restart or migration.

Headless Chrome reproduced the old 403 with Origin:null on both hostnames. After
the one-header change both native form submissions sent the matching origin and
displayed the dashboard, using synthetic credentials and an in-memory database.
No real admin password or persistent database mutation was used in that browser
test. Safe before/after evidence is in ignored `.work/admin-origin/`.

Origin-fix validation: 27 panel/startup tests passed; relevant device/network/
attendance/isolation backend regressions passed with 111 tests and three opt-in
tests skipped (114 total, including the panel tests). Actual headless Chrome
completed native-form login, same-origin dashboard navigation and logout for both
local hostnames. The running port 8003 panel was restarted and both login URLs
were checked for the corrected response header. No persistent record was changed.

The browser behavior follows the [Fetch Standard's Origin-header algorithm](https://fetch.spec.whatwg.org/#append-a-request-origin-header).

## Credentials and scope

`panel-admin.json` is created only inside the existing private manual-android
environment directory, inheriting that directory's restricted permissions. It
contains the chosen username and a PBKDF2-SHA256/600,000-iteration salted password
hash, never a plaintext password. It is also ignored by Git. The initializer
refuses to overwrite an existing file; repeated startup does not rotate any key,
password, template or registration. Forgetting the password requires a separately
reviewed local credential reset; there is no reset HTTP endpoint.

Admin sessions are opaque server-side memory records, rotated at login and
revoked at logout, with an absolute 30-minute lifetime. Restart signs everyone
out. Cookies are HttpOnly and SameSite=Strict. HTTP is restricted to localhost;
do not publish this listener or reuse this transport design on a remote host.
Only one operator should use the UI during a demonstration. Five failed logins
within five minutes throttle further attempts for that process.

All mutations, including login/logout, require a session-bound CSRF token and
same-origin POST. Mutating management forms consume/rotate the token; reload
another open tab if its token becomes stale. GET does not change database rows.
Responses are no-store, escaped HTML with no JavaScript or external resources.
Host and actual connection-peer checks reject remote/DNS-rebinding requests;
forwarded headers cannot authorize access. Uvicorn proxy-header processing and
access logs are disabled. No passwords, PINs, tokens or cookies are logged by the
panel.

The launcher uses the existing `load_profile`, network guard and `operator_engine`.
It validates the real server's port, schema, account, datadir and MariaDB version
before serving, and has no root/.env/production fallback. The existing private
`fyp_manual_admin` database credential is used as an operator credential; it is
powerful and must remain private. This panel adds no account/grant. Its requests
can only call a fixed set of existing services, never arbitrary SQL, shell
commands, migration functions or PowerShell. This is suitable for the disposable
test environment only, not an internet-facing least-privilege admin deployment.

Before each database page/action, the configured backend must pass the existing
`/manual-test/isolation` contract (disposable, port 3322, account-bound policy and
production-port guard), and the existing process-identity guard must match this
private environment's backend profile. Missing/stopped/wrong backends fail closed. Optional
classroom selection additionally requires the backend's classroom attendance
route and the relevant schema. Missing optional tables show FEATURE_SCHEMA_UNAVAILABLE;
the panel never creates or migrates them automatically.

## Pages

1. **Attendance Sessions**: select an existing course and optional group when
   ambiguous, duration in minutes (same-day window), and an existing classroom
   if required. A successful creation shows the six-digit PIN in a result card
   with **Copy PIN**. Open sessions can regenerate the PIN after confirmation.
   This invalidates the previous PIN for new submissions. The replacement is
   displayed once after commit. PINs and hashes are absent from the table.
   Session and policy actions update the displayed table in place. Closing a session
   retains its dates, attendance and verification history; existing enforcement
   rejects closed sessions. Overlaps/missing classes/invalid duration are errors.
   This page creates attendance *sessions*, never attendance records.
2. **Network Policies**: list all CIDRs, add an enabled simulation policy, enable
   or disable existing simulation policies. This reuses `fyp_test.change_policy`
   and the existing canonical CIDR validation/audits. Non-simulation policies are
   read-only. Both IPv4 and IPv6 syntax are supported. Adding does not prove the
   real network is authorized: final verification still uses actual ASGI source IP.
3. **Classroom Wi-Fi**: add a classroom/AP policy with BSSID and optional SSID,
   enable/disable it, retain audit history. Existing operator semantics enable
   newly added Wi-Fi entries. A classroom requirement is attached to a session
   only by explicitly selecting it during creation. Signed client observations
   remain weaker than cryptographic proof of physical classroom presence.
4. **Experimental BLE**: list/add/enable/disable service-UUID policies. New BLE
   entries are disabled. Defaults (5 samples, -65 dBm, 15 seconds) are experimental,
   not calibrated. BLE is **not enforced by attendance**. The current physical
   BLE_EVIDENCE_FUTURE issue is not fixed or bypassed by this panel.

Changing a policy affects existing verifier behavior immediately, as with the
terminal tools. Do not disable a policy during a PASS demonstration accidentally.
No deletion, student/device/template editing, approval issuing, replacement,
face recovery or attendance editing is provided.

## Partner laptop and ordinary port 8000

The panel is separate from both student HTTP ports. No changes are made to
`application_factory.py`, `main:app` or the ordinary port 8000 configuration.

The fastest reproducible setup is to provision a **separate disposable environment**
on the partner's computer using the existing manual-environment guide and pinned
schema/account rules, run its isolated backend on 8002 and database on 3322, then:

```powershell
.\start-admin-testing.ps1 -Environment 'C:\FYP\DB-DeviceManagement\manual-android-<PARTNER_ENV>' -InitAdmin
.\start-admin-testing.ps1 -Environment 'C:\FYP\DB-DeviceManagement\manual-android-<PARTNER_ENV>'
```

Replace the placeholder with the actual private environment path. Do not copy
another person's operator credentials, database files, .env, enrollment templates
or keys. Existing provisioning scripts reference this laptop's MariaDB/phpMyAdmin/
PHP locations; those prerequisites must be reviewed on another laptop. No portable
environment is assumed merely from a Git checkout.

`-BackendPort 8000` is supported as an **explicit readiness target**, not permission
to manage the partner's original database:

```powershell
.\start-admin-testing.ps1 -Environment '<PARTNER_PRIVATE_ENV>' -BackendPort 8000 -CheckOnly
```

An ordinary `uvicorn main:app` on 8000 does **not** expose `/manual-test/isolation`
or install the classroom Wi-Fi/BLE routers and classroom attendance adapter. The
check therefore rejects it, intentionally. `/` returning "Backend running" is
not sufficient evidence. There is no claim that the current ordinary 8000 database
can be administered by this isolated panel. A later shared deployment needs an
explicit reviewed database/identity adapter and schema/grant validation; do not
remove the check, point at 3306, or enable experimental enforcement to get past it.

Required existing schema for these features:

- Core academic/session and network policy/audit tables.
- For Wi-Fi: existing classroom Wi-Fi migration, including Phase 3 requirement
  snapshots and bindings when sessions require classrooms.
- For BLE: existing standalone four-table BLE migration, only if using that page.
- For Slot 2: the existing device-management migration, school provisioning and
  matching enrollment revision, explicit ACCOUNT_BOUND_FYP demo setting and fresh
  server authorization. This panel neither implements nor bypasses those steps.

No schema or permission migration is introduced by this panel. Validate missing
migrations on a backed-up restored disposable copy using the existing guides;
never run them blindly against a partner's shared/production database. Ordinary
port 8000 remains supported for the app independently of the panel.
